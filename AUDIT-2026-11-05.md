## 1. Verdict

The **core engine is in good shape**: download → convert → tag → Spotify copy
works on real links, editing a synced song is genuinely non-destructive to the
audio, covers and catalogue lookup behave, undo works, the dark/light palettes
are coherent, and 599 tests pass.

The **risk is concentrated in three places**:

1. **The Spotify panel can destroy a playlist.** Its mirror algorithm deletes
   everything it did not see, and it can see an empty or partial Local Files
   index, a deleted folder, or a zero-track folder. The user's real library
   already contains a zero-track folder (`Vocaloid`). One click on **Sync
   playlist** there empties that playlist.
2. **The panel's edit/review paths silently erase album and track number.**
   `/api/metadata` treats omitted fields as "clear", and three panel dialogs
   omit them. This is data loss with a success toast.
3. **The desktop is polished but has several first-class UI defects at its own
   documented minimum size** (title column 44 px), plus input loss on Enter
   during a job, a broken search state after any reload, and a dialog that
   starts a rewrite if you press Enter on open.

Scorecard (my judgment, not a reviewer score): **functionality 8/10,
data safety 5/10, UI/UX 6.5/10, panel completeness 5/10, tests 7/10,
docs accuracy 6/10.** The plan below is ordered to raise data safety and the
1000-px experience first.

## 2. Defect register

Legend — **Verified**: `R` = reproduced at runtime, `C` = certain from code,
`S` = reported by static review, verify while fixing. Severity: **B**locker
(data loss / core action impossible), **H**igh, **M**edium, **L**ow.

### 2.1 Blockers — data loss or a core action that destroys work

**B1. "Sync playlist" deletes songs it merely failed to see** — `R`
`musicdlp/services/spotify_sync.py:192-200`, `spicetify/.../index.js:144-168`
`to_remove = current - seen`. `seen` contains only URIs matched *this run*. If
`LocalFilesAPI.getTracks()` returns `[]`/incomplete (first scan, Spotify
scanning, folder not yet indexed, tags just edited), every playlist URI is
"not seen" and removed. Reproduced: an empty local list produced
`to_remove = [existing local URI, hand-added track URI]`. The panel applies it
immediately with no preview and no confirmation.
**Fix:** the panel sends `local_files_complete` (count > 0 and a fresh
`LocalFilesAPI` read); the bridge must refuse to plan removals when it is not
true. Add a dry-run preview dialog (N add / N remove / N unmatched) with
"Remove N songs" as a non-default, destructive-styled button. Never remove
anything when the folder has zero tracks without an explicit typed confirmation.

**B2. Sync on a stale/unknown/renamed folder wipes the playlist** — `R`
`index.js:568-572,700-724` loads folders only at startup/after add/after job;
`bridge.py:438-445` returns `[]` for an unknown id; `build_plan` then removes
everything. Reproduced with `folder_id=999999` → `to_remove=[only URI]`.
Renaming a folder in the desktop creates a new playlist and orphans the old.
**Fix:** bridge returns `404 Unknown folder` for an id that does not exist;
panel refreshes folders before a sync and aborts if the folder vanished;
moderately: the panel gets a **Refresh** control and a rename path.

**B3. Panel review dialogs erase album and track number** — `R`
`bridge.py:465-483`, `index.js:355-365,416-435,479-498`
`ReviewDialog.apply` posts only `title`/`artist`; `_set_metadata` writes
`album=""` and `track_number=None`. Reproduced: album `Album X`, track `4` →
`None/None` after translating a title. This silently destroys "Number as
album" and "Look up details" results in both the translate and AI flows.
**Fix:** make the bridge's metadata write a **partial update** (only keys
present in the body), and have each dialog send the complete set of fields it
owns. Add a bridge test asserting that a title-only PATCH preserves album and
track, and a panel-level contract test.

**B4. Bridge mutations race a running pipeline** — `C` (same mechanism as
desktop guard, verified absent)
`bridge.py:465-526,685-726`; desktop blocks these with `_blocked_by_job()`.
`/api/metadata` can set `needs_update=1` between a convert stage's read and
its final write, which hard-sets `needs_update=0` (`pipeline.py:986-993`) —
the DB says the new name, the file keeps the old one, and the "needs update"
flag that would fix it is gone. `_cover_bulk` and `_rewrite` can rewrite a file
while `ffmpeg.convert` is `os.replace`-ing it (Windows sharing violation), and
`_gdrive` can copy a half-written file.
**Fix:** one shared `_mutation_guard` in the bridge that refuses (409 + clear
message) while `pipeline.is_running` or an add/cover job is running; the panel
shows "Music DLP is busy" and keeps the dialog open. Long jobs should be queued
or refused, never started silently.

**B5. A stale Spotify copy is deleted even when its replacement failed** — `C`
`pipeline.py:1091-1103` deletes `_stale_spotify` unconditionally; the guard
only checks the *new* source names. If `SpotifyService.sync` fails (folder
unwritable, disk full, locked), the song is already flagged `sync_error`, then
the old file is unlinked — the song disappears from Local Files although the
delivery failed.
**Fix:** only unlink a stale copy for a track whose sync succeeded in this run
(`result.done`), and keep a per-track "old copy" map rather than a flat list.

**B6. Applying a video cover cancels a pending metadata rewrite** — `C`
`library.py:511-516` writes `needs_update=0`; `set_cover`/`restore_video_cover`
preserve it. Panel path: edit title → apply video picture → the row no longer
offers "Needs update", the file keeps the old name/tags. Existing test
(`test_cover_apply.py:86`) cements the wrong behaviour.
**Fix:** preserve the flag; update the test to assert it is *not* cleared.

### 2.2 High — misleading success, broken feedback, broken core UX

**H1. Table is unreadable at the documented 1000-px minimum** — `R`
Measured at 1000×620: table viewport 472 px, columns `[32,38,44,150,58,0,136,0]`
— **the Title column is 44 px**, showing `DRAK…`, `夜…`, `Balat…`. At the same
size Pro mode hides Format (viewport 472 < 560), although README promises it.
The responsive breakpoints (`track_table.py:469-491`) hide Artist at 440 px but
keep Title at Stretch with no minimum, so fixed columns win.
**Fix:** width budget that reserves ≥ 220 px for Title before showing
Artist/Length; show Format in Pro from 430 px or drop the README promise; verify
at 1000×620 with 125 % scaling.

**H2. Any reload leaves an invisible library search and loses the return link** — `R`
`main_window.py:860-866`. While the library-wide search is active,
`_load_source` re-applies the query to the table's hidden filter, then clears
the top box and sets `_search_from = None`. Reproduced: box empty, filter
`at the gates` still applied, 2 of 4 rows visible, no visible indication why;
clearing the (now empty) box cannot return to the previous link. The existing
test (`test_a_reload_keeps_the_library_search_applied`) only checks the table
filter, so it passes.
**Fix:** never clear `search_edit` from `_load_source`; only `_on_global_search`
owns it. Preserve `_search_from`. Extend the test to assert the top box text,
filter visibility, and return-link behaviour.

**H3. Enter in the link box during any job silently discards the pasted link** — `R`
`main_window.py:1362,1386`. `_add_from_input` clears the box, then
`_add_links_text` refuses with "Wait…". The Add button is disabled but the
line edit and `returnPressed` are not. Reproduced: box empty, only `_last_add_text`
holds it, no restore path.
**Fix:** do not clear until the job starts; disable the edit while busy (or
accept and queue); restore `_last_add_text` on refusal; add a test.

**H4. Opening Edit details and pressing Enter immediately rewrites and resyncs** — `R`
Initial focus is the **Save** button (`footer.py:48` sets it default; nothing
focuses the title on open), and `update_check` is pre-ticked for converted
songs (`track_details.py:152`). One Enter without looking starts
convert(+sync). `Settings` has a milder version (focus on the tab bar, Enter
saves).
**Fix:** focus the title field on open; make the destructive checkbox require
an explicit click when the dialog was opened by Enter; keep Enter=Save but only
after the user has visited a field (or focus the title always).

**H5. Cancel does nothing during "Fix covers" and can lead to a DB close under the worker** — `C`
`main_window.py:2061-2074` handles only pipeline/add; `_is_busy()` includes
`_covers_running`; `status.set_busy()` shows Cancel. `closeEvent` then asks
"Cancel and exit?", `_cancel()` no-ops, and after 8 s `db.close()` runs under
`FixCoversTask`.
**Fix:** add a covers cancel event checked between songs; have `_cancel` cover
all three; make close refuse (or wait) until the task completes.

**H6. Sorting is discarded on every reload** — `R`
`track_table.py:344` calls `sortByColumn(COL_POSITION, Ascending)` on every
`set_source`; a job finish, edit save, or refresh resets the user's sort.
**Fix:** remember `(column, order)` per view and restore it; also reset the `#`
column to view order when sorted by another column (currently row numbers look
scattered).

**H7. "Clear selection" clears only the current view, leaving the count** — `R`
`main_window.py:501` → `model.clear_checks()`, which is per-source, while
`_on_checked_changed` merges and deliberately keeps other links' ticks.
Reproduced: 4 ticked → Clear → 1 ticked, button still "(1)". The label doesn't
say "in this view".
**Fix:** label it "Clear selection in this view" and add "Clear all selections"
(Ctrl+Shift+D or menu), or make it global — pick one and say so.

**H8. The inspector is stale while a song is processed** — `R`
`main_window.py:1973-1976` only updates the table row; the inspector shows
"Not downloaded" while the pill says "Downloading".
**Fix:** if `inspector.current_row.track.id == track_id`, refresh the inspector
row from the model.

**H9. Successful Spotify sync can be reported as "FFmpeg is needed"** — `C`
`main_window.py:2029`: the `not ffmpeg.available` branch precedes
`summary.get("synced")`, so a sync-only run on a machine without FFmpeg shows
"download… FFmpeg is needed to convert them" and still fires the "Sent to
Spotify" notification.
**Fix:** order the checks: cancelled → failed/fatal → synced → no-FFmpeg.

**H10. The panel reports success for jobs that never started** — `R`
`bridge.py:422-436` emits and returns `{"started": true}` unconditionally;
the GUI refuses when busy (`main_window.py:1945`). Reproduced: `stages:
["bogus"]` → `started: true`; `["bogus","download"]` also starts a download
and later `KeyError`s on `index_by_stage[stages[0]]`. The panel then polls
`/api/status`, sees the *old* job, and reports done.
**Fix:** bridge validates stages against `Pipeline.STAGES`, waits for the GUI
to answer (queued call returning bool), and returns `{"started": false,
"reason": …}` on refusal. Panel surfaces it.

**H11. Panel busy state clears after ~1 s for every non-pipeline job** — `C`
`index.js:635-650` polls `/api/status`; if `pipeline_running` is false it
reloads and clears `busy`. Add/Sync/Drive/Translate/AI/cover jobs are bridge
jobs, not pipeline jobs, so buttons re-enable mid-operation, progress
disappears, and a second Add can start.
**Fix:** track the job id associated with `busy` and wait for *that job's*
status, not the global pipeline flag.

**H12. Panel "Download to Spotify"/"Convert"/"Send to Spotify" bypass the
desktop preflight** — `C`
`index.js:919-937` sends every ticked row; the desktop filters to downloaded
rows or prompts (`main_window.py:1889-1920`). Empty selections produce a job
that does nothing, or errors with no summary. Also, starting the sync stage
from the panel calls `spotify.restart()` and **kills Spotify, closing the
panel** (`pipeline.py:1091-1092`, `spotify.py:116-160`,
`spotify_auto_restart` defaults true).
**Fix:** send only eligible rows and report "N skipped (not downloaded)"; add a
panel/desktop setting or a `restart: false` option for panel-started jobs.

**H13. Panel Edit → "Update the audio file now" does not force a rewrite** — `C`
`index.js:268-274` posts `force: true` but not `retag`; `start_pipeline_for_bridge`
passes `force` only. The bridge comment claims this was fixed. Verify against
`bridge.py:422-436` and `main_window.py:1924-1936`: `retag` is never set, so a
song with an existing file and changed name goes down the normal convert path —
which happens to work only because `pipeline.py:769` now also retags on
`track.needs_update` (uncommitted change). Make it explicit and tested.
**Fix:** bridge accepts `retag` and forwards it; panel sends it.

**H14. Panel "Rewrite files" is weaker than the desktop action** — `C`/partly `R`
`bridge.py:710-726` → `maintenance.rewrite_tags`, which does **not** rename
files, does **not** update the Spotify copy's *name*, does **not** clear
`needs_update`, and uses `"Singles"`/`display_track` instead of the playlist
album/position fallback the converter uses (`maintenance.py:286-287` vs
`pipeline.py:816-819`). It does rewrite tags in existing Spotify copies
(verified — the static review was wrong on that point). The panel always says
"Files rewritten and the Spotify copies updated." and discards `notes`.
**Fix:** route the panel action through a pipeline job (`convert`, `retag=True`,
`only_synced=True`) exactly as `_update_files` does; show notes.

**H15. Panel always translates artists, ignoring the desktop setting** — `C`
`bridge.py:583` `bool(body.get("translate_artist", True))`; the panel never
sends the field. A user who unticked "Artists too" on the desktop still gets
artists translated from the panel.
**Fix:** default from `self.settings.translate_artist`; send it from the panel.

**H16. Panel "Fix covers" has no video-still fallback** — `R` (kwargs `{}`)
`bridge.py:515-523` calls `refresh_cover(id)` without `thumbnails=self.thumbnails`
(the desktop passes it at `main_window.py:174-176`); songs with no catalogue
cover are reported `unchanged` instead of falling back to the upload picture.
**Fix:** pass thumbnails; assert in a bridge test.

### 2.3 Medium — paper cuts that add up

**M1. Toast messages are hidden behind panel modals** — `C`
`index.js:978` renders `Toast` before the dialogs; `.mdlp-toast` has no
`z-index` while `.mdlp-overlay` is `z-index: 1000` (`style.css:186-206`). Every
error from Edit/Review/Album/Lookup is invisible until the dialog closes. The
toast also never auto-dismisses.
**Fix:** render the toast last with `z-index: 1100`; auto-dismiss after 8 s and
add a close affordance.

**M2. Panel has no confirmation for a destructive sync** — `C`
`index.js:922` calls `doSync` directly. The README admits hand-added songs are
removed, but a single misclick can remove a curated playlist. Fixed together
with B1's preview.

**M3. Catalogue lookup can return a different Drake song** — `R`
`lookup("Drake", "At The Gates")` returned **"Care Package 2", track 4,
score 100**, which is almost certainly a different recording (the leak has no
official release). The guard checks the main artist and title, but "At The
Gates" also exists as a real Drake track, so score alone cannot tell them
apart. Also, the returned artist is the *release* credit
("Drake, Lil Uzi Vert") rather than the queried one.
**Fix:** show the release year/album and a "Not the right song" option;
require the release year to be plausible for a leak? (No — that's wrong for
official songs.) Better: present candidates and default to unchecked when
score < 90 or the album is a compilation/bootleg whose title does not appear in
the song's metadata; never apply without review. This already goes through
review — add a confidence/notes column and don't pre-tick suspicious matches.

**M4. Panel playlist reads are not paginated and writes are not chunked** — `C`
`index.js:146-148` `PlaylistAPI.getContents(uri)` with no `offset/limit`;
`148` maps whatever page arrives as the whole playlist, so out-of-page entries
are treated as absent (duplicate adds allowed) and stale entries beyond the page
are never removed. `:157-159` adds every URI in one call (Spotify limits ~100).
**Fix:** loop `getContents(uri, {offset, limit})` until exhausted; chunk adds and
removes in 100s; report partial failure per chunk.

**M5. Duplicate metadata collapses two songs into one playlist entry** — `R`
Two different files with identical title/artist/album/length produce one
`spotify:local:` URI (`spotify_sync.py:192-194`); both were counted as matched
and only one URI was planned. The files themselves are kept apart by
`unique_path` (`Same Name.mp3`, `Same Name [m1].mp3`), but Spotify will only
show one.
**Fix:** surface a "two songs have identical tags" warning before sync; offer
"edit one of them" (the desktop already has duplicate detection, which does not
catch two *different* uploads with the same final metadata).

**M6. Panel's sync toast says "up to date" when songs are unmatched** — `C`
`index.js:711`; only matched songs are up to date. Fix the copy.

**M7. Panel ignores `needs_update` and `sync_error`; dead status labels** — `C`
`bridge.py:186-205` sends raw `status`; the panel reads only `status`
(`index.js:188-239`). A deleted file still shows "Converted"; an edited song
shows "In Spotify"; `STATUS_LABELS.needs_update/missing` and
`style.css .missing` are unreachable. Fix by sending `display_status` (with
`file_missing`) or exposing derived fields.

**M8. Panel empty/offline recovery is incomplete** — `C`
The 5 s health poll never reloads folders or tracks after coming back online;
with zero folders the panel never calls `/api/tracks`; there is no manual
refresh; a 403 is reported as "token mismatch" even when the real cause is
Origin/CORS.
**Fix:** on reconnect, reload folders+tracks; add Refresh; distinguish 403
auth from CORS/network.

**M9. Panel is fixed-width and clips long content** — `C`/screenshot
`style.css:85-90` `220px 1fr`, `overflow:hidden` on the table wrap, no ellipsis
on `.mdlp-title`/`.mdlp-folder`, table renders every song. At Spotify's side
panel, long titles expand rows and the status column can be cut off.
**Fix:** `minmax(150px, 220px) 1fr`, `text-overflow: ellipsis`, horizontal
scroll or a card layout under 520 px, and virtualize/paginate beyond 200 rows.

**M10. Panel light themes are broken** — `C`
`.mdlp-input`/`.mdlp-btn`/`.mdlp-table-wrap` use white-on-dark translucency;
`.mdlp-modal` hardcodes `#282828`. On a light Spotify theme inputs are nearly
invisible and modal text can be dark-on-dark. Use Spotify's CSS variables
(`--spice-text`, `--spice-card`, `--spice-button`) with fallbacks.

**M11. Dead root selector** — `style.css:3-9` styles `#musicdlp-root`, which is
never created (Spicetify renders the component into its own container), so the
intended padding/min-height never apply.

**M12. Desktop: setup banner actions always open step 1** — `C`
`main_window.py:284` → `_open_setup` → `SetupDialog` → `_show_step(0)`. "Show
me how" (Spotify) lands on the FFmpeg page; the user must click Next 2–3 times.
**Fix:** pass a target step (`SetupDialog(..., start_step=3)`).

**M13. Desktop: no bridge controls anywhere in Settings** — `C`
`settings.py:1142-1146` only carries `bridge_enabled/port/token` through on
save. README says "Turn it off in Settings". Add a small **Spotify panel**
section (enable, port, "reconnect panel" button) or correct the README.

**M14. Desktop: "Settings saved" can be false** — `C`
`_open_setup` always says "Setup saved." even on Close (`main_window.py:3107`);
`_open_spotify` ignores `OSError` on save and still says "Spotify folder
saved." (`3231-3238`); theme/mode save failures are swallowed (`3080,3214`).
**Fix:** report the real outcome; offer retry.

**M15. Desktop: settings can be held hostage by an unavailable folder** — `C`
`settings.py:1065-1104`: `_save_now` refuses the whole dialog if the Spotify or
output folder is empty/unwritable, so changing the theme or log level is
blocked while a drive is disconnected. **Fix:** save everything else, warn
about the folder, and keep the dialog open with that tab selected.

**M16. Desktop: Help → Keyboard shortcuts is clipped and lists one shortcut
that cannot work** — `R` (one label clipped at 640 px) `shortcuts.py:43-57`;
Backspace also removes songs (`track_table.py:41`) but is undocumented;
"Shift+Enter starts a new line" applies only to the Bulk Add dialog, not the
single-line link box. **Fix:** wrap descriptions, add Backspace, correct
Shift+Enter.

**M17. Desktop: a cancelled or interrupted conversion can leave `Song.tmp.mp3`** — `C`
Uncommitted work fixes the cancelled path (`ffmpeg.py` try/except) but not an
unexpected `OSError` from `os.replace` (locked/AV), and `clean_partial_files`
is never called. **Fix:** clean tmp on all failure paths and call the existing
`clean_partial_files` at startup.

**M18. Desktop: `raw_path` is not remapped when the output folder is repaired** — `C`
`maintenance.py:91-104` remaps only mp3/m4a. `keep_raw` downloads stay in the
old tree and are fetched again; `_move_tree` silently skips name collisions and
still switches the setting to the new folder (`maintenance.py:57-88,124`).
**Fix:** remap raw too; on a collision, keep the file, note it, and do not
switch folders until the merge is clean (or suffix the moved file).

**M19. Desktop: config with malformed JSON is silently replaced and then
overwritten** — `C`
`config.py:173-179` returns defaults on any `OSError/ValueError`; startup then
calls `ensure_bridge_token()` → `save()`, which overwrites the unreadable file.
A damaged config loses folders, API key, token with no backup. **Fix:** on a
parse failure, rename the bad file to `config.json.bad-<timestamp>` and log +
tell the user; only then write defaults.

**M20. Desktop: `sync_error` sticks after a later successful rebuild** — `C`
Only the sync stage clears it (`pipeline.py:1064-1068`). A convert-only run, a
relink, or a metadata edit leaves rows showing "Error" while their audio is
fine. **Fix:** clear `sync_error` on a successful convert when the Spotify copy
is known to be missing? No — clear it only when the file is rebuilt *and* the
copy state is unknown → set `needs_update`? Safer: keep it, but label it "Spotify
copy needs sending" and offer Retry; or clear on convert and let the next sync
re-add. Decide explicitly.

**M21. Desktop: Google Drive re-sends create duplicates for same-named songs** — `C`
`gdrive.py:209-265,228` looks up the manifest by *source* name after assigning
a *target* name, so `01 - Intro.mp3` from a second song becomes `(2)`, then

**Decisions and deviations:**

- The fingerprint is not a frame hash: it is size + duration + head/tail
  SHA-256. It is cheap, works without FFmpeg, and is refreshed after every
  write Music DLP makes. Files written by an older version have no
  fingerprint until rewritten or converted again; README says so. A retag
  or a cover change is therefore not reported as an outside change.
- Automatic backups are daily + before an upgrade, not before every
  destructive operation. A pre-delete backup on each removal would copy the
  whole database for every click; the daily snapshot is the safety net, and
  **Back up now** is one press away.
- Restore requires a restart instead of swapping an open SQLite file.
- The panel duplicate remover keeps files by default, unlike the desktop
  dialog where the user chooses at removal time.
